# Init Docs — Workflow

Produces `docs/handbook/` — a human onboarding handbook. Self-contained skill: the scan, catalog, interview, and generator all live inside this folder. Works for backend, frontend, full-stack, and monorepo projects.

Signal detection here mirrors the scan used in sibling skills such as `init-agent-docs`. When adding new stack signals, update both skills. This is a documentation-level dependency, not a file-level one.

## Preconditions

Before Phase 1:

1. **Handbook collision check** — if `docs/handbook/` already exists, ask the user: **abort** (default) or **write to `docs/handbook-<YYYYMMDD-HHMMSS>/`**. Never merge, never overwrite. User edits may be present.
2. **Read existing root docs as inputs** (never mutate):
   - `README.md` — source material for `getting-started.md`
   - `CONTRIBUTING.md` (or `.github/CONTRIBUTING.md`, `docs/CONTRIBUTING.md`) — source for `contributing.md`
   - `AGENTS.md` — triggers conditional `for-llms.md` + may seed the handbook index
   - `docs/agent/*.md` — supplemental signal for seeding handbook prose (see Phase 1d for freshness check)

## Phase 1: Scan

Scan the entire codebase before talking to the user. Produce a **signal inventory**, not a summary.

### 1a. Baseline (always)

- **Stack**: languages, frameworks, runtime (check `package.json`, `Cargo.toml`, `pyproject.toml`, `go.mod`, `Gemfile`, `composer.json`, `mix.exs`, etc.)
- **Package manager**: npm/pnpm/yarn/bun/cargo/pip/poetry/uv/go/etc.
- **Scripts / commands**: `package.json` scripts, Makefile, justfile, Taskfile
- **Existing docs**: `README.md`, `CONTRIBUTING.md`, `AGENTS.md`, `docs/`, `docs/agent/`, `.github/`, any `.md` files in repo root
- **Linter/formatter configs**: biome/eslint/prettier/rustfmt/ruff/black/golangci → informs conventions doc
- **Folder tree**: top-level + one level deep in `src/` (or equivalent)

### 1b. Signal detection

For each candidate doc in [CATALOG.md](CATALOG.md), check whether its signal fires. Record matches. Common signal classes:

**Project shape**
- Monorepo: `apps/` + `packages/`, `turbo.json`, `nx.json`, `pnpm-workspace.yaml`, `lerna.json`, Cargo workspace
- Modular / DDD: `features/`, `modules/`, `contexts/`, `bounded-contexts/`
- Layered: `domain/`, `application/`, `infrastructure/`, `core/`, `adapters/`, `ports/`, `usecases/`

**Backend** (dependency + folder combined)
- ORM: drizzle-orm, prisma, typeorm, sqlalchemy, ecto, active_record
- Auth: better-auth, next-auth, clerk, auth0, passport, devise
- HTTP framework: hono, express, fastify, nestjs, koa, axum, gin, fastapi, rails, django
- Jobs: croner, node-cron, bullmq, bee-queue, sidekiq, celery, rq
- Infra: Dockerfile, docker-compose, fly.toml, k8s manifests, terraform

**Frontend**
- Meta-framework: next, remix, tanstack, nuxt, sveltekit, astro, gatsby, react-router v7
- UI lib: shadcn, @radix-ui, @mui, @chakra-ui, @mantine
- Styling: tailwindcss, styled-components, @emotion, vanilla-extract, @pandacss
- State: @reduxjs/toolkit, zustand, jotai, pinia, vuex, mobx, @xstate
- Data: @tanstack/react-query, swr, @apollo/client, urql, rtk-query
- Forms: react-hook-form, formik, vee-validate + zod/valibot/yup
- i18n: next-intl, react-i18next, @formatjs, vue-i18n
- Stories: `.stories.tsx`/`.stories.ts`, `.storybook/` folder
- Flags: launchdarkly, growthbook, unleash, posthog, statsig
- Telemetry: @sentry/*, posthog-js, @datadog/browser-rum, segment, mixpanel
- Build: vite, webpack, turbopack, rspack, esbuild config files

**Testing / CI**
- Test runners: vitest, jest, playwright, cypress, pytest, go test
- CI: `.github/workflows/`, `.gitlab-ci.yml`, `.circleci/`, `buildkite/`

### 1c. Enumerate bounded contexts

If `features/`, `modules/`, `contexts/`, `packages/`, or `apps/` exists at a consistent level, list each subdirectory by name. Each becomes a candidate per-feature/module doc.

### 1d. Agent docs as supplemental signal

If `docs/agent/` exists, read every `.md` inside. For each file:

1. Extract factual claims — stack names, dep names, folder paths, tool names mentioned in its body.
2. Cross-check claims against the current scan's signal inventory.
3. Classify:
   - **FRESH** — no contradictions. Eligible as seed material: the opening paragraph of the matching handbook doc may be generated by rephrasing this agent doc into human voice.
   - **STALE** — at least one key claim contradicts scan (e.g., doc says "Prisma" but deps show `drizzle-orm`). Do not use as seed. Record for the completion report's "Stale agent docs" section.
4. "Matching handbook doc" = same filename (e.g., `docs/agent/auth.md` seeds `docs/handbook/auth.md`).

Agent-voice bullet lists must be rephrased into full sentences when seeding. Do not copy structure verbatim.

### 1e. Do not ask the user for anything derivable from the codebase.

## Phase 2: Propose

Present a proposal shaped by the scan. Structure:

```
Detected:
- <stack summary>
- <project shape>
- <N bounded contexts: list>
- Existing root docs: <README.md ✓ / CONTRIBUTING.md ✓ / AGENTS.md ✓ / docs/agent/ ✓>
- Agent docs status: <N FRESH (will seed) / M STALE (ignored)>

Proposed handbook docs for docs/handbook/:

Always-on:
  1. getting-started.md — <"summarize root README + interview first-run gaps" OR "interview (no README)">
  2. contributing.md — <"summarize root CONTRIBUTING.md + link-back" OR "interview (no file)">
  3. tech-stack.md — scanned deps + path aliases
  4. conventions.md — <linter/formatter detected>
  5. workflows.md — <detected scripts>
  6. glossary.md — seeded from <bounded context names> + interview for extras
  7. design-decisions/ — ADR folder

Signal-driven:
  8. architecture.md — <signal that fired>
  9. data-model.md — <signal>
  ...

Per-bounded-context (under features/):
  - <name>.md for each detected context

Conditional:
  - for-llms.md — <docs/agent/ detected, will add pointer page>

Design decisions to capture as ADRs (tick which ones need rationale write-up):
  [ ] ORM: <detected lib>
  [ ] Auth: <detected lib>
  [ ] HTTP framework: <detected lib>
  ...

Skip any? Add others? (reply with numbers to skip, ticks for ADRs, or describe additions)
```

Rules:

- Propose every fired signal — user skips what they don't want.
- When root `CONTRIBUTING.md` or `README.md` is present, annotate the corresponding always-on doc as "summarize + link"; when absent, annotate "interview".
- If bounded contexts exist, always propose per-context docs under `features/`.
- Candidate ADR choices are listed in [CATALOG.md](CATALOG.md#design-decisions--proposal-driven). Only propose ones whose signals fired.
- If >15 candidates, group under headers (Architecture / Backend / Frontend / Ops) for readability — still propose all.

Wait for user response. Record approved docs, skipped docs, ticked ADR decisions.

## Phase 3: Interview

Grill-me style. **One question at a time.** Every question ships with a **Recommended** answer and **Why**. Number globally (**Q1:**, **Q2:**, …). Never reset per topic.

### Rules

- Explore the codebase before asking. If the answer is in the code, read the code.
- Follow implications — when the user answers, pick the next question *because* of that answer.
- Block on "I don't know" when the answer gates a downstream decision; explain what's blocked.
- Skippable questions: user may say "skip" / "TBD". Generated prose will carry a visible `**TODO:**` marker or `Rationale: TBD`.

### Question budget

- **One headline question per approved handbook doc** — shape:
  > "One-paragraph headline for `<doc>`: what should the opening paragraph say to a new engineer encountering this for the first time?"
- **One rationale question per ticked ADR** — shape:
  > "Why `<chosen tool>` over alternatives? One-paragraph answer is enough."
- **One glossary question** — "List 3–10 domain terms a new engineer won't know with one-line definitions."
- **One story question per bounded context** — "Story for `<context>`: who uses it, why it exists, anything a new engineer must not break?"

### Skipping the headline question

Skip the headline question for a doc when either:

1. **Source file covers it** — `contributing.md` when root `CONTRIBUTING.md` exists; `getting-started.md` when root `README.md` has install/run sections. Summary from source replaces the interview answer.
2. **FRESH agent doc covers it** — e.g., `docs/agent/auth.md` is FRESH, so the handbook's `auth.md` opening paragraph is rephrased from the agent doc without asking the user. User still reviews during draft.

Explicitly tell the user when a question is being skipped for either reason so they can re-insert one if they want custom phrasing.

### Stop condition

Every approved doc has a resolved opening (from interview, source file, or FRESH agent doc) OR a recorded `**TODO:**`. Every ticked ADR has rationale or `Rationale: TBD`. Do not proceed to Phase 4 until this is true.

## Phase 4: Generate

Create `docs/handbook/` (or the alternate path resolved in Preconditions).

### Frontmatter

Every `.md` gets:

```markdown
---
title: <Human-readable title>
last_updated: YYYY-MM-DD
---
```

### File-by-file generation

- **`README.md`** (GitHub-visible, not rendered by VitePress) — install + run instructions for the local reader. Template in [VITEPRESS.md](VITEPRESS.md#github-readme).
- **`index.md`** — VitePress homepage. Project title, 2–3 sentence description (derived from scan + interview headline for "overall project"), "Start here → getting-started.md" link, a brief teaser of the sidebar groups.
- **`getting-started.md`** — summarized from root `README.md` (install, clone, run) + first-run command from detected scripts. Opening = interview headline. If source was thin, interview answers fill body; `**TODO:**` markers on gaps.
- **`contributing.md`** — summarized from root `CONTRIBUTING.md` with link back to the root file as canonical. If no root file, interview answers. Opening = interview headline.
- **`glossary.md`** — seed entries from bounded context names with `**TODO:**` definitions; append user-supplied terms.
- **Signal-driven docs (tech-stack, architecture, data-model, etc.)** — content frame from scan; opening paragraph from interview headline (or rephrased FRESH agent doc); document capabilities and concepts, not file paths (except for `architecture.md` and `canonical-shape.md` where folder shape is load-bearing).
- **`design-decisions/README.md`** — index table of ADRs: title + status + date.
- **`design-decisions/template.md`** — copy of the ADR template from [CATALOG.md](CATALOG.md#adr-template) for future use.
- **`design-decisions/NNNN-<slug>.md`** — one per ticked decision. Context + Decision populated from scan. Rationale from interview, or `TBD — fill in when the chooser is available.` if skipped.
- **`features/README.md`** — table listing each bounded context with one-line summary from interview story.
- **`features/<name>.md`** — opening paragraph = interview story; body documents capabilities/flows from scan.
- **`for-llms.md`** (only if `docs/agent/` or `AGENTS.md` detected) — one page pointing agent readers to the machine-readable docs at `docs/agent/` / `AGENTS.md`, noting that VitePress can't render them because they sit outside the handbook srcDir.
- **`.gitignore`** — always write:
  ```
  node_modules/
  .vitepress/cache/
  .vitepress/dist/
  ```

### TODO marker convention

Inline in prose, always surface user skips:

```markdown
> **TODO:** <what's missing — why only a human can fill it>
```

Keep markers on their own blockquote line so they render visibly in VitePress and on GitHub.

### Content voice rules

See [CATALOG.md](CATALOG.md#content-voice). Short paragraphs, why alongside what, link out to framework docs instead of re-explaining, cross-link with relative paths.

## Phase 5: VitePress (optional)

After all markdown is written, ask the user:

```
Install VitePress locally so you can preview the handbook with sidebar and search? [Y/n]
```

If **no** → skip this phase; completion message still lists docs and a run-without-VitePress note.

If **yes** → follow [VITEPRESS.md](VITEPRESS.md). Pre-flight `node --version` ≥ 18, detect package manager, write `package.json` + `.vitepress/config.ts`, install, print dev command.

If pre-flight fails → skip install with explanation; docs remain generated; run-command note points user to install Node ≥18 and re-run the skill (or install manually).

## Completion

Emit a structured report:

```
Done — docs/handbook/ created.

Files created:
- docs/handbook/README.md
- docs/handbook/index.md
- docs/handbook/getting-started.md
- <full list>

Open TODOs (sections only a human can finish):
- <file>: <what's missing>
- ...

ADR rationales marked TBD:
- design-decisions/NNNN-<slug>.md — <decision name>
- ...

Stale agent docs (not used as seed — consider updating):
- docs/agent/<file> — <conflict detected>
- ...

VitePress status: <installed ✓ | declined by user | Node <18, skipped>

Run the local reader:
  cd docs/handbook && <detected-pm> run dev

Next:
  1. Open the dev server and skim the handbook end-to-end.
  2. Fill the TODOs and TBD rationales.
  3. Re-run this skill after significant architecture changes to regenerate scanned sections (the skill refuses to overwrite an existing docs/handbook/ — use the alternate-path option).
```

Omit report sections that have no entries (no TODOs = no TODO section, etc.).
